# 种草工坊流程检查与修复记录

日期：2026-09-24  
范围：原创种草工坊四阶段、原任务恢复、成图审核、文案、交付导出、批次持久化及刷新入口。  
交付状态：本地源码已修改并验证；未部署、未提交 Git commit；未请求真实付费生图或文案服务。

## 1. 结论

截图中的四张「结果待恢复」不能直接等同于四次确定失败。请求超时、响应丢失、停止轮询、刷新页面，都可能发生在上游已经受理甚至已经计费之后。直接把这些任务当作普通失败重试，存在重复计费风险。

本次修复以三项约束为主：

1. **结果不确定时先查旧任务，不自动重新提交。**
2. **异步结果只能修改它对应的那一版任务，不能覆盖新任务或手工编辑。**
3. **保存没有确认成功时不能静默切换批次；审核失败不能触发付费重做。**

同时补齐了四宫格重试、分析结果失效、自动流水线状态同步、文案有效性、审核后导出规则、刷新入口和交付页面的状态表达。

## 2. 全流程梳理与检查范围

| 环节 | 主流程 | 本轮检查 / 整改重点 |
| --- | --- | --- |
| 进入与恢复 | 首页进入或 URL 直达 → 读取活跃批次 → 恢复快照 | 开发模式刷新不再被首页状态覆盖；刷新只恢复状态，不自动提交生图 |
| ① 采集商品 | 输入商品标识 → 解析 → 并发采集 → 商品与图片池 | 核查解析、采集并发、失败重试及选中商品边界；执行中禁止切换批次 |
| ② 选图与配置 | 选参考图 → 拍摄架构、资产、镜数、模型与比例配置 | 自动选图后立即分析要读取新图片；配置变化使旧分析失效；相同珠宝架构不重复触发失效 |
| ③ 分镜分析 | 视觉分析 → 分镜结果 → 人工确认提示词 | 分析重复点击保护、异常退出清理、编号唯一性；单商品重分析不扰动其他商品的任务复用 |
| ④ 生图执行 | 就绪校验 → 任务合并 → 单镜 / 四宫格提交 → 轮询与保存 | 提交不确定性、取消时机、幂等键、新旧任务隔离、部分失败重试 |
| 原任务核对 | 按 upstream task ID / 本地 taskKey 查询 → 恢复图或切片 | 只查询旧任务；四宫格可重新切片上传，但绝不借恢复入口重新调用生图模型 |
| 成图审核 | 采用 / 重做 / 淘汰 → 保存 → 审核接口 | 先保存再审核，审核成功再重做；淘汰图片保留预览和重新审核入口，但不参与文案、ZIP、Excel 交付 |
| 文案 | 自动 / 单品 / 批量生成 → 手工编辑 → 重写 | 使用当前可交付成图；图片或提示词变化时丢弃过时响应；不覆盖请求期间的手工编辑 |
| 交付 | 预览 → 单图下载 / 单品包 / 批量包 / Excel | 继续沿用永久结果及失效结果过滤，新增审核淘汰过滤；保留失败下载记录，不把缺图假装成功 |
| 批次管理 | 自动保存 → 新建 / 复制 / 归档 / 历史 / 重载 | 保存结果必须被确认；运行中禁止切换；未保存重载需明确确认；实际流水线状态写入快照 |

说明：采集、存储、真实网关的既有测试纳入全量回归；未在真实商家页面、生产数据库或付费服务上进行端到端试跑。

## 3. 问题清单与已实施修复

严重程度：P1 为可能重复计费、错用结果或丢失内容；P2 为状态、操作一致性或可用性问题。

| 等级 | 发现的问题 | 已实施的修复 |
| --- | --- | --- |
| P1 | 生图 POST 丢失响应后被当作普通失败，可再次提交 | 新增明确的 `recoveryRequired` 错误标识，网络异常、异常响应、超时等待等进入待核对态；自动提交和失败重试均受阻断 |
| P1 | 响应是错误但携带上游任务 ID 时，任务 ID 可能丢失 | 先保存 `taskId`，再处理失败；例如上游受理成功但本地写库失败，仍保留后续核对依据 |
| P1 | 用户在 POST 等待期间停止任务，会在解析响应前退出，遗失已受理任务 | 先读取已返回的受理标识，再结束等待；取消只表示停止本地等待，不伪装为上游取消 |
| P1 | 只有 taskKey、没有 upstream ID 的任务缺少核对入口 | 增加按 taskKey 查询；明确失败解除恢复门禁，查询失败或仍处理中继续保留门禁 |
| P1 | 四宫格失败重试继承旧主图、切片信息、任务 ID 或审核结果 | 每次明确重做新建 attempt 并清理旧来源、输出与审核状态；仅重试失败切片，不覆盖已成功切片 |
| P1 | 相同提示词的重做可能复用被标记过期的旧幂等记录 | 合并时保留对旧记录的识别，对 superseded 任务推进 attempt，不复用旧成功输出 |
| P1 | 旧异步生图 / 核对响应可能覆盖替换后的任务 | 回写匹配任务 ID、幂等键和对应的旧任务状态；版本不符不落到新任务 |
| P1 | 批次保存失败仍可新建、复制或归档，造成当前内容丢失 | `flush()` 返回是否确认保存；切换前必须成功；未保存离开有提醒，重载服务器版本需确认 |
| P1 | 成图刚生成就审核，服务器尚未保存该任务；审核失败仍可能重做 | 审核前 flush；审核成功后再执行重做；按任务去重，旧审核响应不污染新输出 |
| P1 | 「淘汰」只改变按钮状态，图片仍可进入文案和交付 | 区分“可预览图片”和“可交付图片”；淘汰 / 待重做结果排除出文案输入、Excel 和两种 ZIP 路径 |
| P2 | React 更新尚未提交时，后续流水线读到旧 itemsRef | 引入同步更新 ref 的 items setter，自动选图后的分析、生成完成后的自动文案读取最新商品状态 |
| P2 | 单商品重分析推进全批次分镜版本，影响其他商品复用 | 不再提升全局分镜版本；仅使对应商品旧任务过期，清理对应旧文案和四宫格结果 |
| P2 | 镜头编号重复 / 非法，或失效配置仍可进入失败重试 | 新增镜号校验；失败重试也执行选图、分析、镜数、提示词就绪校验 |
| P2 | 刷新把尚未提交的排队任务误判为已付费待恢复 | 未提交 PENDING 保持排队；运行中或持有提交 / 四宫格恢复信息的任务才进入待核对 |
| P2 | 分析异常后 busy 标记滞留；重复点击启动并行分析 | 使用 in-flight 标记及 finally 清理；单商品分析异常给出提示；新一轮分析重置旧取消控制 |
| P2 | 文案响应回来时，成图 / 提示词已经换版 | 记录文案源签名，源变化时不应用过时文案并提示重试；保持既有手工编辑保护 |
| P2 | 页面和保存的批次状态长期停留 draft，或遗留暂停 / 取消状态 | 根据采集、分析、生成、待核对和成图结果派生实际状态；批次切换重置运行控制 |
| P2 | URL 直达 / 刷新在 React StrictMode 下可能回到首页 | URL 初始化完成后才允许把当前视图反写 URL，避免初始化和同步互相覆盖 |
| P2 | 交付页顶部将待核对任务显示为失败，错误文本挤占卡片 | 统一待核对与确定失败计数；待核对使用黄色；长错误可展开；明确重复计费警告和按钮含义 |

## 4. 修复后的关键行为

### 4.1 看到「结果待核对」怎么办

1. 优先点击 **核对原任务**。
2. 查询到成功：恢复原图，不再调用生图模型；四宫格会继续切片、上传。
3. 查询到明确失败：允许用户发起下一次重试。
4. 仍在生成 / 查询失败 / 没有记录：继续保留待核对，不自动重投。
5. 确实需要放弃旧结果时，用户确认可能重复计费：
   - 顶部 **放弃恢复，允许重做** 只解除门禁，不立即发起生图。
   - 单卡 **放弃恢复并重做** 确认后执行该镜头的新尝试。

**如果请求在上游受理后、本地保存上游任务 ID 之前超时，且服务端也没有可查的 taskKey 记录，本次修复不能凭空还原上游任务。此类旧任务仍须结合网关任务记录核实。**

### 4.2 审核与交付

- 采用：保留可交付结果。
- 淘汰：图片仍能预览和再次采用，但不会进入新的文案输入、ZIP 或 Excel 图链接。
- 重做：审核先落库，成功后才新建生图尝试；审核失败不会偷偷生图。
- 未审核图片仍保留原有可导出行为；本轮没有强制所有图片必须先采用才能导出，以免改变既有工作方式。
- 单图下载作为主动查看 / 留档操作仍保留；批量交付遵守淘汰过滤。

### 4.3 保存保护

- 自动保存采用既有 revision 乐观锁，不能用未经确认的本地内容切换批次。
- 保存异常后采用保守阻断，不静默覆盖服务器版本。
- 「重新加载」若会丢弃本地修改，必须确认；仍有生产任务运行时不能绕过切换保护。
- 本轮没有新增离线草稿仓库或多端冲突合并界面，因此不能将“保护未保存内容”理解为离线永久保存保证。

## 7. 后续架构改进建议（本轮未冒充已完成）

1. **持久化提交收据 / 后端可靠队列。** 在调用上游前持久化请求意图，补偿查询受理结果；前提是网关提供可用的幂等或请求追踪能力。单纯增加超时时间不能消除受理不确定性。
2. **服务端持续运行与恢复。** 目前浏览器停止等待不等于上游停止，也不等于浏览器关闭后本地排队任务会继续执行。若要支持关页后自动完成，需要后端任务执行器或回调机制，不应靠前端自动重发。
3. **保存冲突处理体验。** 后续可增加离线快照下载、服务器 / 本地差异预览及显式恢复保存，避免用户只剩重载服务器版本这一路径。
4. **完整运行台账。** 本轮使快照状态跟随实际执行，但没有把所有阶段改造为服务端事件驱动工作流，也没有补写完整的历史 run/event 台账。
5. **真实环境稳定性。** Comfly / 其他网关超时率、模型成图质量、远程图片跨域、临时 URL 的真实有效期，需要测试环境和服务端日志验证，不能由本地模拟测试给出保证。

## 7. 追加整改：从首页重进仍显示上次任务（2026-09-24）

### 根因

首页「种草工坊」入口只切换视图，没有表达“开始新创作”的意图；工作区挂载后始终读取服务端活跃批次。把“重进”和“刷新恢复”当成同一行为，导致用户反复看到上次的商品和任务。

### 修改后的入口约定

| 操作 / 情况 | 行为 |
| --- | --- |
| 首页「种草工坊：开始创作」 | 消费一次性的新批次意图；保存确认后归档旧批次，再进入空白的第 1 步 |
| 当前批次已空 | 复用空批次，不重复制造空历史记录 |
| 只粘贴链接、尚未采集 | 输入文本也属于内容：先保存并归档，不静默清掉 |
| 刷新 / 直接打开工坊 URL | 不触发归档，恢复当前批次和任务 |
| 从首页重新进入时仍在采集、分析、生成或写文案 | 不切换批次，提示任务执行中；首页往返不卸载工坊，后台结果仍回到原批次 |
| 保存失败 / 归档失败 | 保留现有内容并显示错误，不假装已经开始新批次 |
| 原先停在历史预览或配置浮层 | 新入口关闭旧预览 / 配置，不让旧界面盖住新批次 |

旧商品、图像任务及结果继续保存在历史批次中；本次不删除历史数据，也不自动重发生成请求。

### 防竞态与关联修复

- 新入口意图只放在内存 Store，不写入持久化草稿；刷新不会再次归档。
- 同步认领入口意图，防止 StrictMode 重复执行；切换期间锁住批次操作、暂停自动保存，并显示准备状态，避免旧商品闪回或用户继续修改即将归档的内容。
- 先排空保存队列并确认保存，再归档；批次加载只采纳最新请求的响应，旧响应不能把内容覆盖回来。
- 有失败 / 待核对任务但没有成功图片时，也允许保留第 4 步；不再因“无成功图片”误回到采集页。
- 首页入口不采用遗留 URL 阶段覆盖恢复内容；直接打开 URL 仍校验可进入阶段。
