# 种草工坊：端到端复盘与分层重构

日期：2026-09-24。状态：第一阶段整改已实现，尚未部署。

> 结论：需要结构性重构，但不建议推倒重写。保留采集、分镜编译、生图适配、幂等恢复和历史批次能力；重构资产准入、制作方案校验和导航/状态呈现。后端持久任务编排应另立阶段迁移，不能以这次前端整改宣称已完成。

## 一、为什么看起来像“功能强行拼在一起”

不是按钮数量本身的问题，而是几套业务契约不一致：

1. **资产管理不等于可生产资产，却共用了含糊的“资产库”文案。** 分类列表隐藏某些记录，全量 slim 选项没有同样过滤；分类列表带 registry，全量列表缺失 registry。用户在一处看到 0，另一处却能选“无法确认”。
2. **页面对生产模式的说明与执行器不同。** 实际分镜生成必须有完整四图母本，空态却声称“退回拍摄架构兜底”。拍摄架构是规则，不是完整图组母本的替代品。
3. **不同入口的校验不一致。** 单款分析、批量分析、辅助自动选图、手动资产锁定各有局部规则；分析还会拿封面偷偷兜底，生图却要求用户已经确认参考图。
4. **资源页面与创作阶段混在一个路由中。** 资产库仍显示 step=4，生产预设入口在资源页能打开一个被隐藏的创作子树内弹窗。
5. **执行事实、完成状态与提示文案混淆。** “辅助选图并分析”被称为全自动生产；配置窗固定宣称实时保存成功；选过图便称“已就绪”，但缺母本/资产失效时根本不能分析。
6. **状态所有权过于集中。** runner 同时管理采集、模型、锁定、分析、生图、文案、恢复和批次持久化；domain 已有阶段 gate，但 1–3 阶段并没有统一由这些 gate 驱动。已有 stage4 服务端完成门禁不能等同于全链路已经状态机化。

这些判断来自本地代码追踪和提供的截图；没有直接读取线上数据库，因此不能推断线上到底有多少有效资产，也没有删除任何历史数据。

## 二、应当形成的产品主线

```text
进入工坊
  ├─ 首页主动进入 → 新创作意图；原批次有内容则先保存/归档
  ├─ 刷新或深链接 → 恢复原批次，不重复创建任务
  └─ 历史查看 → 明确只读，不与当前生产混用

1. 商品准备 → 导入/采集、确认成功商品和参考图
2. 制作方案 → 确认拍摄架构、母本来源、可选替换、输出规格
   └─ 分析前校验：图片/资源加载/母本适配/锁定有效性
3. 分镜审核 → 检查每镜提示词及实际绑定，明确点击后才生图
4. 生成交付 → 进度、未知任务核对、采用/淘汰/重做、文案、导出

资源管理（图组、人物、穿搭、场景 / 拍摄架构 / 商品类目）
  └─ 独立准备区；返回当前创作，不新建、不覆盖批次
```

### 母本、架构、替换项的职责

- **拍摄架构**：商品类目的拍摄规则和提示词约束。
- **四图母本**：镜头顺序、构图、场景、动作、出镜范围的来源；当前后端流程必需。
- **人物/穿搭/场景**：可选替换，不选就沿用母本，不要求为了“凑齐配置”创建假资产。
- **仅手部/静物图组**：不硬塞人物脸部与穿搭替换。
- **资源管理列表**：允许管理待审、修复、停用等资产；**生产选项**只列通过资格校验的已发布资产。两者不应机械要求数量相等，但必须明确解释差异。

## 三、端到端检查结果与处理

| 环节 | 根因或风险 | 本次处理 | 验证/边界 |
|---|---|---|---|
| 重进/刷新 | 新创作意图与恢复旧批次混用 | 保留前轮已实现的意图分流、先保存归档、运行中阻止切换 | 重进专项浏览器回归；不删除历史 |
| 采集/选图 | 分析擅自使用未确认封面，自动选图可能改动未选商品 | 分析只接受已选参考图；辅助选图只作用于选中且采集成功商品 | 纯逻辑测试；已有采集浏览器回归 |
| 资产分类列表 | 对 description/top/bottom 整串正则过滤，误伤局部服装 | 按主体名称识别占位身份，不用下装“无法确认”否定可用袖口 | 占位与有效局部穿搭测试 |
| 全量生产选项 | slim 丢失发布状态、内容可用性与类目匹配字段 | all/slim 补齐 registry/provenance/contentEligible 和图组分类信息；共享准入函数 | UI 模拟 full/slim 语义，类型检查 |
| 生命周期 | 手工锁定可绕过发布校验，母本轮换池没统一发布过滤 | 人物/场景/穿搭锁定、手工母本、自动母本均受已发布查询约束 | 共享策略单测；真实数据库集成仍待预发 |
| 资源缓存 | 工坊只在挂载时复制一次；错误变成空数组 | 缓存失效通知、焦点刷新、请求序号保护；显式加载/失败状态及重试 | 浏览器加载失败、停用后刷新选项移除 |
| 分析入口 | 校验散落，等到提交后才发现配置无效 | 单款/批量/辅助分析共用 preflight；批量任一不满足即停止整批提交并给出商品原因 | 无效锁定时分析 POST=0、生图 POST=0 |
| 分析并发 | 队列缺省 16，负数无执行且无解释 | 缺省 2、归一化并限制 1–6，尊重取消 | 队列单测 |
| 配置变更 | 出镜模式/库开关变化不触发重分析；商品 effect 强制覆盖开关 | 相关变更失效分镜；移除每次珠宝商品更新强制打开资源开关 | 类型/回归；保留历史快照恢复 |
| 运行中编辑 | 顶部入口可绕过局部按钮禁用 | 设置窗口执行中只读，避免运行中混用新参数 | UI disabled fieldset；既有任务切换保护 |
| 导航 | 资产页带创作 step；资源入口没有返回当前任务语义 | 资源页使用 tab，不再写 step；明确资源管理说明和返回当前创作 | 切换/刷新路由浏览器测试 |
| 保存提示 | 无条件“实时自动持久化” | 显示批次真实等待/保存/失败状态 | 失败提示专项及此前保存失败回归 |
| 生成恢复 | 超时不能确定上游是否已经收费受理 | 保留前轮 GET 核对/新尝试键/禁止未知结果盲目重投 | 原有生成恢复浏览器与单测 |
| 交付 | 淘汰图可能进入批量导出/文案 | 保留前轮有效结果过滤与旧版本隔离 | 原有审核、文案与导出单测 |

### 数据兼容约束

- 不删除“不适用”等记录，只禁止它们进入生产选择；后续数据治理应先导出审计，再决定归档。
- 无 registry 的历史记录沿用现有 grandfather 兼容规则；不在列表 GET 中批量写库或强迫所有旧资产重新审核。
- 已有 registry 为待审/停用/归档的记录不再因手动锁定而绕过限制。上线后旧批次可能显示“原选择已失效”，应由用户重选或沿用母本，而不是静默换人换衣。
- 明确手选母本沿用已有行为；自动母本仍按商品类目适配与持久轮换。没有擅自强制改变手动跨类目创作政策。
- 未审核图片仍保留既有主动导出能力；淘汰/要求重做的图片不进入批量交付。没有在本轮强推“必须全部点击采用才可下载”。

## 四、代码层面的分层决策

### 已落地的第一阶段

1. `packages/domain/src/workshopPipeline/assetEligibility.ts`：纯业务准入规则；前后端复用。
2. 资产 API 保留列表/选项/详情所需元数据，服务端召回先做发布限制；卡片和详情禁止将待审、停用或不完整资产应用到生产，应用处理器再次检查。不能只靠前端隐藏选项。
3. `workshopAnalysisPreflight.ts`：统一无副作用的分析前校验；实际入口在任何模型 POST 前调用。
4. `useWorkshopAssetLocks`：负责资源加载状态、缓存失效同步和待应用绑定，不再把失败伪装成空库。
5. 设置窗口与流程总览展示事实；资源导航与创作阶段分离。设置弹窗通过 portal 脱离父级层叠上下文，补齐键盘关闭、焦点循环和焦点恢复；未持久化的修改明确显示“等待保存”，不宣称已实时落库。
6. 保留前轮实现的 generationLifecycle / recovery / delivery 边界，不重写稳定的供应商适配与恢复路径。

### 第二阶段：统一制作方案与版本契约（未实施）

将当前 settings 散字段收敛为版本化 ProductionPlan：

- selected product IDs + confirmed reference IDs；
- architecture + group source strategy + active replacements；
- model route + output specification + concurrency；
- plan revision / storyboard revision / execution revision。

服务端增加明确的 validate-plan 返回：阻断项、警告项、每款分配来源、预计镜头数和请求数。前端展示计划，用户确认后冻结版本；所有阶段从同一派生结果决定按钮可用性，逐步替代散落判断，而不是再加一套只供展示的状态机。

验收：单款/批量/辅助入口得到相同阻断结果；换图、换母本、改提示词都能准确解释哪些结果过期；任务与冻结计划版本一致。

### 第三阶段：持久化后端任务编排（未实施）

浏览器当前仍承担大量队列调度。页面 keep-alive 不等于关浏览器后能继续完整生产。

- 后端持久化 analysis/generation/copy/export 作业及 attempt；
- 每步存输入版本、上游 ID、受理时间、终态与恢复依据；
- 支持按服务端作业查询，而不是依赖一个长存活的 React hook；
- 客户端负责发起、查看、审核和恢复意图，不负责唯一的生产进度事实；
- 保留原供应商适配层，按工作区灰度，避免改编排时同时改所有模型协议。

验收：刷新/关页/断网/多端查看不丢任务；不重复计费；取消能区分“停止后续提交”和“上游已受理任务”。

### 第四阶段：资产治理与质量闭环（未实施）

- 占位记录独立归档建议，不自动删除；发布时校验真实可复用内容。
- 标记“完整穿搭/局部穿搭/仅手部”，不要靠名称正则长期承担全部内容判断。
- 母本构图质量、商品一致性、审核结果和实际交付效果形成可解释指标。
- 资产检索从全量加载转为面向商品、类目、资格的分页查询；registry 回填从热路径迁移到显式作业，避免每次分析全表兼容回填。

## 五、验证方式与上线边界

本地工程验证：`pnpm run check` 全链路通过，包含类型检查、依赖边界、未使用代码检查、密钥扫描、**298/298 测试**及生产构建。ESLint 为 **0 errors / 703 warnings**，warning 并未在本次全部消除；运行时为本机 Node 24.19，仓库要求 Node 22，正式环境应再用仓库指定版本验收。

三组浏览器回归均使用本地 Vite 和模拟接口，通过覆盖：

- 资产准入一致性、草稿应用禁用、局部穿搭保留、服务失败不冒充空库、失效锁定零分析请求、停用后选项刷新。
- 资源页地址/刷新恢复、保存确认后刷新配置不丢失、返回原创作批次。
- 明确分析一次 → 分镜审核前零生图请求 → 确认后四次生图 → 交付可见。
- 设置窗口 portal 层级、900px 无横向溢出、Escape 关闭、无浏览器运行时错误。
- 此前的未知任务 GET-only 核对、重试确认、审核失败不生图、保存失败阻止切换，以及重进/刷新/运行中保护。

测试暴露的时序边界：自动保存不是同步写入，直接在保存确认前强制刷新不能当作已保存恢复用例。UI 已区分等待保存/保存中/成功/失败，原有离开提醒保留；回归在收到保存确认后再检查刷新恢复。脚本可复跑：

- `tools/scripts/qa/workshop-assets-browser.mjs`：生产选项/资源管理一致性、加载失败、失效锁定不提交、资源路由恢复、分镜审核后生成交付。
- `tools/scripts/qa/workshop-browser.mjs`：未知任务核对、审核、收费重试确认、保存失败。
- `tools/scripts/qa/workshop-entry-browser.mjs`：首页重新进入、刷新恢复、空批次复用、运行中切换保护。

所有浏览器 API 都是模拟服务。**没有部署、没有删除生产资产、没有真实调用付费模型，也未验证生产数据库的 registry 历史分布。**

上线顺序建议：测试工作区发布少量完整母本及真实替换资产 → 预发真实完整流程 → 双版本接口兼容检查 → 少量工作区灰度 → 核对调用次数、失败率、恢复成功率与导出完整率。没有通过真实生成质量验收前，不应宣称“整个种草工坊已经彻底重构完成”。
